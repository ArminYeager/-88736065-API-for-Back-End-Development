# คลังคำตอบสำหรับโจทย์ข้อที่ 3: วิเคราะห์ปัญหาและอธิบายสาเหตุ (5 คะแนนเต็ม)

> 💡 **สูตรการตอบ 3 ประโยคเพื่อคะแนนเต็ม:**
>
> 1. **สาเหตุของปัญหา:** โค้ดเดิมเกิดอะไรขึ้นในระดับระบบ
> 2. **ผลกระทบทางธุรกิจ:** หากปล่อยไว้จะเกิดความเสียหายอย่างไร (Data Inconsistency, Crash, Security Hole)
> 3. **แนวทางการแก้ไข:** ใช้หลักการใดแก้ และทำไมหลักการนั้นจึงป้องกันปัญหาได้ 100%

### ข้อ 3.1: การไม่ใช้ Transaction ใน `POST /api/orders`

- **คำถาม:** "เกิดปัญหาอะไรขึ้นกับข้อมูลในฐานข้อมูลในโค้ดเริ่มต้นของ `POST /api/orders` เมื่อรายการอาหารลำดับที่ 2 ล้มเหลวแต่ไม่ได้ใช้ Transaction และการใช้ Transaction แก้ปัญหานี้อย่างไร?"
- **คำตอบ:**
  1. **สาเหตุ:** ในโค้ดเริ่มต้น เมื่อคำสั่ง `INSERT INTO orders` และบันทึก `order_items` รายการแรกสำเร็จไปแล้ว แต่เกิดข้อผิดพลาดในรายการที่ 2 (เช่น สินค้าหมด หรือรหัสเมนูไม่มีอยู่จริง) การทำงานจะตัดจบกลางคัน
  2. **ผลกระทบ:** เกิดปัญหา **Partial Write (Data Inconsistency / Phantom Order)** คือมีแถวใบสั่งซื้อหลักค้างอยู่ในตาราง `orders` โดยที่ไม่มีรายการอาหารในตาราง `order_items` ครบถ้วน ร้านค้าได้รับออเดอร์ที่ไม่สมบูรณ์และตัดสต็อกผิดพลาด
  3. **วิธีแก้:** การใช้ **Database Transaction (`beginTransaction`, `commit`, `rollback`)** ตามคุณสมบัติ **Atomicity ในหลัก ACID** จะรวมทุกคำสั่ง `INSERT` ให้เป็นหน่วยการทำงานเดียวกันทั้งหมด หากมีข้อผิดพลาดแม้แต่จุดเดียว ระบบจะสั่ง `rollback()` ยกเลิกการเปลี่ยนแปลงทั้งหมด คืนฐานข้อมูลสู่สถานะเดิมเสมือนไม่เคยเกิดคำสั่งขึ้น

### ข้อ 3.2: บั๊กการคำนวณ `offset = page * limit` และการต่อสตริง `sort`

- **คำถาม:** "เหตุใดการคำนวณ `offset = page * limit` และการนำ `req.query.sort` ไปต่อสตริง SQL โดยตรงจึงทำให้เกิดบั๊กและความเสี่ยงด้านความปลอดภัย?"
- **คำตอบ:**
  1. **สาเหตุและผลกระทบของ Offset:** การคำนวณด้วย `offset = page * limit` ทำให้เมื่อผู้ใช้เรียกหน้าแรก (`page = 1, limit = 10`) จะได้ค่า `offset = 10` ส่งผลให้ระบบกระโดดข้ามข้อมูล 10 รายการแรกไปโดยไม่ได้ตั้งใจ (หน้าแรกไม่แสดงเมนูแถวที่ 1–10) จึงต้องแก้ไขสูตรเป็น `offset = (page - 1) * limit` เพื่อให้หน้าแรกมี `offset = 0`
  2. **สาเหตุและผลกระทบของ Sort:** การนำ `req.query.sort` ไปต่อ String เข้ากับคำสั่ง SQL (`ORDER BY ${sort}`) โดยตรง ทำให้เกิดช่องโหว่ร้ายแรง **SQL Injection** ผู้ไม่หวังดีสามารถแทรกคำสั่งอันตราย (เช่น `; DROP TABLE menu_items;--`) เข้ามาทำลายระบบได้
  3. **วิธีแก้:** เนื่องจากชื่อคอลัมน์ใน SQL ไม่สามารถใช้ Parameterized Query (`?`) ได้ จึงต้องป้องกันด้วยการใช้ **Allowlist Validation** โดยกำหนดรายการคอลัมน์ที่อนุญาตไว้ล่วงหน้า (เช่น `['id', 'name', 'price', 'available']`) หากผู้ใช้ส่งค่าที่ไม่อยู่ในรายการ ให้ fallback กลับไปใช้ค่าเริ่มต้นคือ `'id'` เสมอ

### ข้อ 3.3: ความจำเป็นของ `finally { connection.release(); }`

- **คำถาม:** "เหตุใดเมื่อเปิด Transaction ด้วย `pool.getConnection()` แล้ว จึงจำเป็นต้องมี `connection.release()` อยู่ในบล็อก `finally` เสมอ?"
- **คำตอบ:**
  1. **สาเหตุ:** `pool.getConnection()` เป็นการยืม Connection จาก Connection Pool ที่มีจำนวนจำกัด (เช่น 10 connections) หากเกิด Exception แล้วไม่มีการสั่ง release ตัว Connection นั้นจะค้างอยู่ในสถานะถูกใช้งาน
  2. **ผลกระทบ:** เกิดปัญหา **Connection Leak** เมื่อมีคำขอผิดพลาดสะสมจนครบจำนวนจำกัด Connection ใน Pool จะหมดเกลี้ยง คำขอใหม่ทั้งหมดจะไม่สามารถเชื่อมต่อฐานข้อมูลได้จนเกิด Timeout และระบบ API จะค้าง (Hung/Crash) ทั้งระบบ
  3. **วิธีแก้:** บล็อก `finally` ใน JavaScript จะถูกประมวลผลเสมอไม่ว่าจะทำงานสำเร็จหรือเกิด Error ในบล็อก `try/catch` การใส่ `connection.release()` ไว้ใน `finally` จึงรับประกัน 100% ว่าทุก Connection จะถูกส่งคืน Pool เสมอ

### ข้อ 3.4: การแยก `app.js` ออกจาก `server.js` (`app.listen()`)

- **คำถาม:** "เพราะเหตุใดในการเขียน Automated Testing ด้วย Supertest จึงต้องแยก `app.js` ออกจาก `server.js`?"
- **คำตอบ:**
  1. **สาเหตุ:** หากรวม `app.listen(port)` ไว้ในไฟล์เดียวกับที่ประกาศ Express เมื่อไฟล์ทดสอบทำการ `require('./app')` ตัวเซิร์ฟเวอร์จะสั่งเปิดพอร์ตบนเครื่องจริงทันที
  2. **ผลกระทบ:** เกิดปัญหาพอร์ตชนกัน (`EADDRINUSE`) เมื่อรันหลายไฟล์เทสต์พร้อมกัน และเซิร์ฟเวอร์จะเปิดค้างไว้ทำให้ Jest ไม่สามารถปิด Process ได้ (`Jest did not exit one second after...`)
  3. **วิธีแก้:** การแยก `app.js` (ประกาศ middleware และ routes) ออกจาก `server.js` (เปิดพอร์ตด้วย `listen`) ช่วยให้ Supertest สามารถจำลองการส่ง HTTP Request เข้าสู่ Express App ได้โดยตรงในระดับ Memory โดยไม่ต้องเปิดพอร์ตจริง ทำให้เทสต์รันเร็ว แยกขาดจากกัน และโปรเซสของ Jest จบการทำงานได้อย่างสมบูรณ์

### ข้อ 3.5: การตรวจสอบ State Transition ในการเปลี่ยนสถานะ Order

- **คำถาม:** "เพราะเหตุใด API อัปเดตสถานะออเดอร์จึงต้องมีเงื่อนไขตรวจสอบสถานะเดิมก่อนเปลี่ยนเป็นสถานะใหม่?"
- **คำตอบ:**
  1. **สาเหตุ:** ลำดับขั้นตอนทางธุรกิจของคำสั่งซื้อเป็นเส้นตรง (`pending` ➔ `preparing` ➔ `delivered` หรือ `cancelled`)
  2. **ผลกระทบ:** หากไม่มีการตรวจสอบ ผู้ใช้อาจยิงคำขอเปลี่ยนสถานะย้อนกลับ เช่น ออเดอร์ที่จัดส่งเรียบร้อยแล้ว (`delivered`) ถูกแก้สถานะย้อนกลับไปเป็น `cancelled` เพื่อขอเงินคืน หรือออเดอร์ที่ยกเลิกไปแล้วถูกนำกลับมาทำอาหารซ้ำ ทำให้ร้านค้าสูญเสียรายได้และสต็อกสินค้าคลาดเคลื่อน
  3. **วิธีแก้:** การใช้ **State Machine Validation** เพื่อตรวจสอบสถานะปัจจุบันก่อนทุกครั้ง หากสถานะปัจจุบันเป็นสถานะสิ้นสุด (Terminal State เช่น `delivered` หรือ `cancelled`) ระบบจะตอบกลับด้วย HTTP Status `400 Bad Request` ป้องกันไม่ให้เกิดการแก้ไขข้อมูลย้อนหลัง
